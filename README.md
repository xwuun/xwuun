## 개발 분야

**Django·Spring 기반 백엔드 개발, AI 서비스 연동, 이미지 분석 및 OCR 기능 구현이 가능합니다.** 팀 프로젝트에서 전체 백엔드를 공동 개발하며 데이터 모델 설계, 인증·권한, API 구현, AI 추론 처리, 프론트엔드 연동과 배포 환경 보완을 수행했습니다.

팀에서 사용하는 프레임워크와 코드 구조, API 규약에 맞춰 개발할 수 있습니다. 역할 분담에 따라 일반 서비스 백엔드부터 AI·CV·OCR 기능 연동까지 담당 범위를 조정할 수 있으며, 기능 구현 이후 통합과 오류 수정까지 참여합니다.

## 주요 구현 경험

### 1. AI 연동 · 데이터 기반 상품 추천 및 상담

**상품 검색 → 모델 호출 → 추천 결과 검증 → 대화·요약 저장**으로 이어지는 상담 기능을 구현했습니다. 모델의 응답을 실제 상품 데이터와 연결하고, 상담 결과를 후속 사용자 기능에서 다시 사용할 수 있도록 구성했습니다.

| 기능 | 구현 내용 |
| :--- | :--- |
| **상품 데이터 검색** | MCM 상품 94개의 상품명·카테고리·소재·사이즈·색상·가격·사용 상황을 검색 근거로 활용 |
| **사용자 조건 반영** | 질문 내용과 온보딩의 예산·관심 카테고리·활동 상황을 반영해 추천 후보 조회 |

| **상담 이력 관리** | 사용자별 채팅 세션·메시지·추천 결과 저장 및 이전 상담 조회 |

### 2. CV 모델 활용 · 하이브리드 이미지 손상 진단

**YOLO 탐지 모델과 멀티모달 비전 모델을 결합한 이미지 분석 파이프라인**을 구현했습니다. 손상 유형과 위치를 분석하고, 두 모델의 결과 비교·재분석·최종 결과 선택을 서비스 로직에 연결했습니다.

| 처리 단계 | 구현 내용 |
| :--- | :--- |
| **이미지 입력** | 사용자 소유 제품과 사진을 연결해 진단 요청·이력 생성 |
| **모델 추론** | 학습된 YOLO 탐지 모델과 멀티모달 비전 모델에서 각각 이미지 분석 수행 |
| **결과 비교** | 두 모델의 손상 종류·개수·위치를 비교해 결과 일치 여부 확인 |
| **재분석 정책** | 결과 불일치 시 두 모델 재실행, 재분석 후에도 불일치하면 멀티모달 모델 결과 선택 |
| **결과 구조화** | 안전·주의·위험 단계, 손상 유형·설명·관리 제안 반환 |
| **좌표 처리** | 탐지 영역과 주요 손상 위치를 백분율 좌표로 반환해 이미지 위 시각화 지원 |
| **이력 관리** | 요청 상태와 분석 결과 저장, 상세 조회·이력 조회 연결 |

#### 비동기 추론 및 상태 관리

이미지 분석을 별도 워커에서 수행하고, 분석 요청과 결과 조회를 분리했습니다.

```text
제품·사진 등록
    ↓
진단 이력 생성 [PENDING]
    ↓
YOLO + 멀티모달 비전 분석
    ↓
결과 비교 → 필요 시 재분석 → 최종 결과 선택
    ↓
성공 [DONE] / 실패 [FAILED]
    ↓
상세 API 조회 → 분석 결과·좌표 표시
```

- 프론트엔드가 상세 조회를 반복해 분석 완료 여부를 확인하도록 상태 제공
- 사진이나 연결 제품 변경 시 기존 결과 초기화 및 재분석
- 분석 결과를 진단 이력과 연결해 이후 케어 안내·예약 기능에서 사용
- 진단 결과의 소유권과 완료 상태를 검증해 후속 API의 접근·입력 조건 관리

### 3. OCR · 영수증 및 보증서 정보 추출

- 영수증·보증서 이미지 입력 및 OCR 서비스 연동

## 기술 설계 및 구현 사례

### 1. AI 응답과 서비스 데이터의 정합성

AI 상담에서는 자연어 응답과 실제 상품 데이터가 동일한 근거를 사용해야 합니다. 상품 검색은 서버에서 수행하고, 검색된 후보를 모델 입력으로 전달한 뒤 최종 추천 데이터도 해당 후보에서 구성했습니다.

| 설계 항목 | 적용 내용 |
| :--- | :--- |
| **검색 근거** | 상품명·카테고리·소재·가격·스타일·사용 상황 등 실제 상품 정보 활용 |
| **사용자 맥락** | 질문과 온보딩 정보를 함께 반영해 후보 검색 |
| **응답 검증** | 모델이 생성한 상품 식별자를 신뢰하지 않고 조회된 상품만 반환 |
| **후속 처리** | 추천 결과와 상담 맥락을 방문 카드·개인화 요약 저장에 연결 |
| **실패 응답** | 요약 생성 실패 시 정상 요약과 구분되는 안내 제공 |

이 구조에서 서버는 상품 데이터와 저장 결과를 관리하고, 모델은 제공된 정보를 바탕으로 상담 문구를 생성합니다. 자연어 생성과 데이터 선택의 책임을 구분해 추천 화면·상담 이력·방문 카드가 같은 상품을 참조하도록 구성했습니다.

### 2. 다중 모델 추론 결과의 통합

이미지 진단에서는 YOLO 탐지 결과와 멀티모달 분석 결과를 서비스에서 사용할 수 있는 공통 정보로 처리했습니다. 손상 종류·개수·위치의 일치 여부를 기준으로 재분석과 최종 결과 선택을 수행합니다.

```text
이미지 입력
   ├─ YOLO 탐지 결과
   └─ 멀티모달 분석 결과
              ↓
     종류·개수·위치 비교
       ├─ 일치 → 결과 사용
       └─ 불일치 → 두 모델 재실행
                       ├─ 일치 → 결과 사용
                       └─ 불일치 → 멀티모달 결과 선택
              ↓
     진단 정보·관리 제안·표시 좌표 반환
```

**통합 과정에서 처리한 항목**

- **결과 선택 정책:** 두 모델의 불일치 상황과 재분석 후의 선택 기준을 명시
- **응답 구조:** 손상 유형, 심각도, 설명, 관리 제안, 좌표를 프론트엔드가 사용할 수 있는 데이터로 반환
- **좌표 표현:** 이미지 위 표시를 위해 탐지 영역과 주요 손상 위치를 백분율 좌표로 제공
- **결과 수명:** 사진·제품 변경 시 이전 결과를 초기화해 현재 입력과 결과의 일치 유지
- **후속 기능:** 완료된 진단을 케어 안내와 방문 예약의 입력 데이터로 연결

### 3. 비동기 작업의 상태와 API 동작

이미지 진단은 요청 생성, 분석 실행, 결과 조회가 서로 다른 시점에 이루어집니다. 진단 데이터를 먼저 생성하고 워커의 처리 결과를 상태에 반영해, 프론트엔드가 대기·완료·실패를 구분할 수 있도록 구성했습니다.

| 상태·사건 | 서버 처리 | 연결되는 동작 |
| :--- | :--- | :--- |
| **진단 요청 생성** | 이력을 생성하고 `PENDING` 저장 | 상세 조회로 진행 상태 확인 |
| **분석 성공** | 결과 저장 후 `DONE` 변경 | 결과·좌표 조회, 완료 진단의 예약 연결 |
| **분석 실패** | `FAILED` 변경 | 실패 상태 확인, 상태 변경 알림 |
| **사진·제품 수정** | 기존 결과 초기화 후 재분석 | 변경된 입력을 기준으로 결과 갱신 |

상태값은 표시용 정보와 API 검증 조건에 함께 사용했습니다. 방문 예약에 진단을 연결할 때는 소유권뿐 아니라 `DONE` 여부와 예약 제품의 일치 여부도 확인합니다.

### 4. API 검증과 데이터베이스 제약의 병행

예약 기능은 입력 형식, 사용자 권한, 서비스 규칙, 데이터 중복을 함께 검증해야 합니다. 각 조건을 요청 검증과 데이터 저장 규칙에 나누어 반영했습니다.

| 검증 범위 | 적용 규칙 |
| :--- | :--- |
| **소유권** | 본인의 제품과 진단만 예약에 연결 |
| **연관 데이터** | 완료된 진단만 연결하고 진단 제품과 예약 제품의 일치 확인 |
| **매장 조건** | AS를 지원하는 공식 케어 매장만 예약 대상으로 사용 |
| **시간 조건** | 미래 일시, 운영시간, 정각·30분 단위 검증 |
| **중복 조건** | 동일 매장·동일 시간의 활성 예약 제한 |
| **변경 가능 필드** | 사용자·예약 코드·상태·생성 시각의 직접 변경 제한 |

serializer 검증으로 요청 오류를 반환하고, DB 고유성 제약으로 활성 예약 중복을 추가로 제한했습니다. 생성과 수정에 동일한 검증 규칙을 적용하고, 취소된 예약의 시간은 다시 사용할 수 있도록 처리했습니다.

### 5. OCR 결과와 사용자 입력의 결합

문서 인식 결과가 일부 누락되어도 제품 등록을 이어갈 수 있도록, OCR 추출과 사용자 보완 입력을 하나의 흐름으로 구성했습니다.

- **인식 단계:** 영수증·보증서 이미지를 OCR 서비스로 전달
- **응답 단계:** 추출한 값과 직접 입력이 필요한 필드를 반환
- **보완 단계:** 사용자가 누락 정보를 입력해 제품 등록 진행
- **관리 단계:** 등록된 제품과 관련 이미지를 사용자 데이터에 연결

자동 추출 결과를 제품 입력의 보조 데이터로 사용하고, 수동 등록도 지원해 문서 인식 여부에 따라 등록 경로가 끊기지 않도록 구성했습니다.

## API 구성 및 데이터 흐름

인증, 일반 서비스 기능, AI 처리 결과를 각각의 API로 제공하고 필요한 데이터를 연결했습니다. 프론트엔드에서는 사용자 행동에 따라 생성·조회·수정 API를 호출하고, 분석 작업은 상태 조회를 통해 결과를 확인합니다.

| API 영역 | 대표 기능 | 주요 검증·처리 |
| :--- | :--- | :--- |
| **인증** | 회원가입, 로그인, 토큰 갱신 | 인증 상태와 사용자 정보 |
| **제품** | 제품 CRUD, 이미지 관리, 문서 추출 | 제품 소유권과 입력 정보 |
| **AI 상담** | 상담 요청, 세션 조회, 방문 카드 저장 | 사용자 세션, 실제 상품 후보, 요약 생성 결과 |
| **진단** | 요청 생성, 상세·이력 조회, 입력 수정 | 소유권, 작업 상태, 분석 결과 갱신 |
| **예약** | 가능 시간 조회, 생성·수정·취소 | 소유권, 진단 상태, 운영시간, 중복 조건 |
| **커뮤니티** | 게시글·댓글·좋아요·스크랩 | 사용자 활동과 관련 데이터 |
| **기록·마이페이지** | 날짜별 기록, 활동·스크랩 조회 | 사용자별 데이터와 화면 조회 조건 |

### 데이터 모델링 범위

- **사용자 중심 데이터:** 프로필·온보딩·알림·상담 세션 등 사용자별 정보 관리
- **제품 중심 데이터:** 제품·이미지·문서·진단·예약의 관계 구성
- **콘텐츠 데이터:** 게시글·댓글·좋아요·스크랩·카테고리의 관계 구성
- **시계열 기록:** 날짜별 증상·감정·메모와 캘린더·기간별 조회 연결
- **상태 데이터:** 진단 처리 상태, 예약 취소 상태, AS 접수 상태를 후속 기능에서 활용
